# 2026.288.2325 — docs: the label is `ai.opencharly.skill` (singular), and a skill node's prose lives in its file

Two claims in this repo's public prose were stale, and the first one had already propagated: it is
the source of a gate in another programme that named a label no image carries.

## Summary

**1. The box skills label is `ai.opencharly.skill` — singular.** `spec/spec/label_consts.go:39`
defines it, a built image carries exactly that key, and asking the charly-native reader for the
plural fails closed. The candy's description and the README both wrote `ai.opencharly.skills`,
which is the form the skills-relocation programme's own objective text carries — every surface that
quoted the objective inherited it, including that programme's acceptance gate for its
`layer-supervisord` pilot. A gate naming a label that does not exist can only pass by accident.

**2. A `skill:` node no longer carries a FULL in-line definition.** The README said it does
("carrying the FULL inline skill definition (metadata + markdown content)", and the same claim in
the capability table). This repo's own `#10` relaxed `#SkillInput` — `name`, `description` and
`content` are OPTIONAL, `family` and `owner` stay required — so a node may carry only the routing
while the file the repo owns carries the prose, which is what the candy's `description:` has stated
since that same change. The README now matches the schema and the description beside it.

Two files, both accounted for:

- **`candy/plugin-harness-kind/charly.yml`** — one line of the `description:`: the label key. The
  description is a published surface (it renders as this plugin's opencharly.ai page), so the
  sentence a reader gets had to name the key that exists.
- **`README.md`** — the same key in its "what it provides" paragraph, plus the two stale
  full-in-line-definition claims (the paragraph and the `kind:skill` table row), rewritten to the
  model the schema and the candy description already state.
